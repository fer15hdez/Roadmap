M1
Principiante · ~8h
Fundamentos de CI/CD y cultura DevOps
Por qué CI/CD existe, qué problemas resuelve, qué destruye si se implementa mal.
›
Objetivos
  • Entender qué es CI, CD (Delivery) y CD (Deployment) y sus diferencias reales
  • Identificar anti-patterns de CI/CD en equipos reales
  • Comprender el modelo DORA y sus 4 métricas clave
Conceptos teóricos en profundidad
  • CI — Continuous Integration: La idea central no es "correr tests automáticamente". Es que los desarrolladores integran código al trunk varias veces al día, detectando conflictos en minutos, no en días. El costo de integración crece exponencialmente con el tiempo. Fundamento: trabajo de Kent Beck y Martin Fowler (Extreme Programming).
  • CD Delivery vs Deployment: Delivery = el artefacto puede desplegarse en producción en cualquier momento. Deployment = se despliega automáticamente. La diferencia es una decisión de negocio, no técnica. Muchas empresas tienen Delivery pero no Deployment por razones de compliance.
  • El problema del "integration hell": Sin CI, cada rama larga acumula divergencia. Al mergear, horas o días de conflictos. CI elimina esto integrando continuamente. Ejemplo real: Google integra en monorepo, todos trabajan sobre main.
  • DORA Metrics: Deployment Frequency, Lead Time for Changes, Change Failure Rate, Mean Time to Recovery. Son el estándar para medir madurez DevOps. Elite performers despliegan múltiples veces al día, con MTTR bajo 1 hora.
  • Anti-patterns críticos: (1) Pipelines de 45 minutos que nadie arregla cuando fallan. (2) No correr el pipeline en cada commit, solo en PRs. (3) Tests que pasan siempre (falsos positivos). (4) Deployments manuales como paso "de seguridad".
Casos de uso reales
  • Amazon (2011): pasó de despliegues de semanas a desplegar cada 11.6 segundos. El driver no fue tecnología, fue cultura: equipos con ownership completo de sus servicios.
  • Equipo de 5 personas sin CI/CD: el "release day" dura 8 horas, hay hotfixes en producción, nadie sabe qué versión corre. Con CI/CD: release en 15 minutos, automático, trazable.
Ejercicios prácticos
  • Mapear el flujo actual de tu equipo (o un flujo hipotético) e identificar cuánto tarda cada fase desde commit hasta producción
  • Calcular las DORA Metrics de un proyecto open source real usando su historial de GitHub
  • Documentar 3 anti-patterns que has visto (o puedes imaginar) y proponer soluciones

M2
Principiante · ~6h
Git avanzado aplicado a pipelines
Estrategias de branching, trunk-based development, tags, hooks y cómo Git define el comportamiento del pipeline.
›
Conceptos teóricos en profundidad
  • Trunk-Based Development (TBD): Todos trabajan sobre main/trunk. Feature flags para código incompleto. Ramas de vida corta (<1 día). Es el modelo que usan Google, Meta, Amazon. El problema de GitFlow en CI/CD: ramas largas = integración cara.
  • GitFlow vs TBD: GitFlow tiene sentido para librerías con múltiples versiones soportadas. Para aplicaciones web/servicios, TBD es superior porque reduce el costo de integración.
  • Conventional Commits: Formato estándar (feat:, fix:, chore:) que los pipelines pueden leer para generar changelogs automáticos, versionar con semver, y decidir qué tipo de release hacer.
  • Git tags y versioning: Los pipelines se disparan con tags (v1.2.3) para releases. La diferencia entre annotated tags (para releases) y lightweight tags (para marcadores internos).
  • Protected branches y pipeline triggers: Cómo configurar qué ramas disparan qué jobs. main dispara deploy a producción. develop dispara staging. feature/* solo unit tests.
Ejercicios prácticos
  • Convertir un repositorio con GitFlow a TBD: definir estrategia de feature flags
  • Configurar conventional commits con commitlint como hook pre-commit
  • Crear un script que lea los commits desde el último tag y genere un CHANGELOG.md automático
Error común: hacer merge de una rama de 3 semanas directamente a main sin squash. El pipeline falla por conflictos que nadie entiende. Solución: ramas de vida máxima 2 días y feature flags para código incompleto.

M3
Intermedio · ~10h
Docker en pipelines CI/CD
Build reproducible, multi-stage builds, tagging semántico, registries privados y seguridad de imágenes.
›
Conceptos teóricos en profundidad
  • Multi-stage builds: La razón de existir es separar el entorno de build del artefacto final. Stage 1: imagen con compilador + dependencias. Stage 2: imagen mínima (distroless, alpine) con solo el binario. Resultado: imagen de producción 10x más pequeña, sin herramientas de build.
  • Tagging semántico en CI: Nunca usar :latest en producción. Estrategia: commitsha corto para trazabilidad (myapp:abc1234), semver para releases (myapp:v1.2.3), latest solo para desarrollo local. El pipeline debe etiquetar con al menos sha + versión.
  • BuildKit y caché: --cache-from para reutilizar capas entre builds del pipeline. Sin caché: build de 8 minutos. Con caché bien configurado: 90 segundos. Cómo exportar/importar caché en GitLab CI.
  • Registries privados: GitLab Container Registry (integrado), Docker Hub, AWS ECR, GCP Artifact Registry. Cuándo usar cada uno. Autenticación con service accounts, no con credenciales personales.
  • Imagen scanning: Trivy, Grype, Snyk. Escanear en el pipeline ANTES de subir al registry. Política: no permitir push si hay vulnerabilidades CRITICAL sin excepción explícita.
Ejercicios prácticos
  • Refactorizar un Dockerfile existente a multi-stage: medir la reducción de tamaño
  • Integrar Trivy en un pipeline de GitLab: el job falla si hay CVEs críticos
  • Configurar caché de capas Docker en GitLab CI con registry como backend de caché

M4
Intermedio · ~12h
Diseño de pipelines CI/CD reales
Anatomía del pipeline, stages, jobs, artefactos, paralelismo, caching, testing y buenas prácticas de diseño.
›
Conceptos teóricos en profundidad
  • Anatomía de un pipeline: Pipeline → Stages (ejecutan en secuencia) → Jobs (ejecutan en paralelo dentro del stage) → Steps/commands. El orden importa: fail fast primero. Tests unitarios antes que integración. Scan antes de push.
  • El principio de fail fast: El primer stage debe ser el más barato y el que más frecuentemente falla: linting, formato, tests unitarios. No ejecutar un build de 10 minutos si el linter falla en 30 segundos.
  • Testing en pipelines: Unit tests (aislados, rápidos, sin I/O), Integration tests (con dependencias reales o mocks pesados), Smoke tests (validar que el deploy funcionó: hit a /health endpoint). Cada capa tiene propósito diferente.
  • Artefactos y dependencias entre jobs: Un job de build genera un binario/imagen. El job de deploy lo consume. No rebuildar en cada stage: pasar el artefacto. GitLab: artifacts: paths. GitHub Actions: upload-artifact/download-artifact.
  • Environments y approvals: dev → staging → production. Promotion manual de staging a prod. Environments en GitLab con protección de rama. Evitar el anti-pattern: deploy a prod sin pasar por staging.
  • Pipeline as Code: El .gitlab-ci.yml vive en el repo. Versiona junto al código. Permite reproducir exactamente el pipeline de hace 6 meses. Es la base de GitOps.
Buenas prácticas de la industria
  • Tiempo máximo de pipeline: <10 minutos para feedback rápido. Si tarda más, paralelizar o dividir.
  • Nunca usar credenciales hardcodeadas en el YAML. Siempre variables de entorno o secrets del CI.
  • Hacer idempotente cada stage: si el pipeline falla y se reejecutar, no debe haber efectos secundarios (no duplicar registros, no redeployar lo mismo dos veces).
Ejercicios prácticos
  • Diseñar un pipeline para una API Node.js: lint → unit tests → build Docker → scan → push → deploy staging → smoke test → aprobación manual → deploy prod
  • Medir el tiempo de cada stage y optimizar el más lento usando paralelismo
  • Implementar un matrix job: correr tests en Node 18, 20 y 22 en paralelo

Intermedio · ~12h
GitLab CI/CD en profundidad
Runners, includes, templates, variables, environments, releases. Comparativa con Jenkins y GitHub Actions.
›
GitLab CI/CD — características clave
  • GitLab Runners: El agente que ejecuta los jobs. Shared runners (GitLab.com), group runners o específicos de proyecto. Executors: Docker (más limpio, aislado), Shell (más rápido, menos seguro), Kubernetes (escalable). Para producción: Docker executor en máquinas dedicadas.
  • include y extends: include permite reutilizar configuración entre proyectos. extends hereda de templates locales. Clave para estandarizar pipelines en empresas con 50+ repos.
  • Variables, secrets y environments: Variables a nivel de instancia, grupo y proyecto. Variables protegidas (solo en ramas protegidas). Variables enmascaradas (no aparecen en logs). Environments para separar prod de staging.
  • Rules vs only/except: rules es el estándar moderno. Permite condiciones complejas: si es tag → deploy, si es MR → solo tests. only/except está deprecado.
  • Releases y versioning: GitLab tiene API para crear releases automáticas desde el pipeline, con changelogs generados desde commits.

M6
Avanzado · ~14h
Kubernetes: deploy, rollout y rollback
Deployments, Services, Ingress, ConfigMaps, Secrets, rollouts estratégicos y rollbacks seguros en CI/CD.
›
Conceptos teóricos en profundidad
  • Deployment vs Pod: Nunca deployar Pods directamente. Un Deployment define el estado deseado y Kubernetes reconcilia. Si un pod muere, el controller lo recrea. En CI/CD: el pipeline actualiza la imagen en el Deployment, k8s hace el rollout.
  • Rolling Update: Estrategia por defecto. Actualiza pods gradualmente (maxSurge, maxUnavailable). Zero downtime si el readinessProbe está bien configurado. Sin readinessProbe: el tráfico va a pods que no están listos → errores.
  • Rollback automático: kubectl rollout undo deployment/myapp. Kubernetes guarda historial de revisiones (revisionHistoryLimit). En GitOps (ArgoCD), el rollback es un git revert, no un comando kubectl.
  • ConfigMaps y Secrets: ConfigMap para configuración no sensible. Secret para credenciales (base64, no cifrado real). Para producción: External Secrets Operator + Vault/AWS Secrets Manager. Nunca secrets en el repo Git.
  • Health probes: livenessProbe (reiniciar si unhealthy), readinessProbe (sacar del Service si no está listo), startupProbe (dar tiempo al arranque). Mal configuradas: causa outages durante deploys.
  • Despliegues progresivos: Canary (10% tráfico a nueva versión), Blue/Green (dos entornos completos, switch instantáneo). Implementación en k8s puro o con Argo Rollouts.
Ejercicios prácticos
  • Deployer una app con Deployment + Service + Ingress en kind local
  • Simular un fallo: deploy de imagen rota, ver que readinessProbe detiene el rollout, hacer rollback
  • Implementar un Canary deployment manual con dos Deployments y pesos en Ingress NGINX
Error crítico: subir a producción un Deployment sin readinessProbe. El rolling update completa aunque la app esté crasheando, porque k8s no sabe que está rota. El resultado: downtime total, rollback de emergencia.

M7
Avanzado · ~10h
GitOps con ArgoCD
El paradigma GitOps, separación de repos app/infra, sincronización declarativa y rollback como git revert.
›
Conceptos teóricos en profundidad
  • GitOps — el paradigma: El estado deseado del cluster vive en Git. ArgoCD sincroniza continuamente el cluster con ese estado. Nadie aplica kubectl en producción manualmente. Toda modificación pasa por git commit → PR → merge → sync automático.
  • Separación app repo vs config repo: El repo de la app tiene el código y el CI pipeline. Cuando CI termina (build + push de imagen), actualiza el config repo (manifiestos k8s con la nueva imagen tag). ArgoCD detecta el cambio en el config repo y sincroniza.
  • ArgoCD Application y AppProject: Application define qué repo/path sincronizar con qué namespace. AppProject agrupa aplicaciones con políticas de seguridad (qué repos pueden deployar a qué namespaces).
  • Sync policies: Manual (aprobación humana antes de aplicar) o Automatic (ArgoCD aplica inmediatamente). Self-heal: si alguien hace kubectl apply manualmente, ArgoCD revierte al estado del repo.
  • Rollback en GitOps: No es kubectl rollout undo. Es git revert del commit que cambió la imagen tag, seguido de merge. ArgoCD detecta el cambio y sincroniza. El rollback es auditable, revisable, y revierte exactamente lo que el commit cambió.
  • Kustomize y Helm con ArgoCD: ArgoCD soporta nativamente Kustomize (overlays por entorno), Helm charts y plain YAML. Para multi-entorno: un chart de Helm, valores diferentes por entorno (values-staging.yaml, values-prod.yaml).
Ejercicios prácticos
  • Instalar ArgoCD en kind, crear una Application que apunte a un repo de manifiestos
  • Implementar el flujo completo: CI actualiza imagen tag en config repo → ArgoCD sincroniza automáticamente
  • Simular un rollback GitOps: git revert + merge, verificar que ArgoCD revierte el cluster
Buena práctica: mantener el config repo con estructura por entorno: /envs/staging/ y /envs/production/. ArgoCD tiene una Application por entorno, cada una apuntando a su directorio.

M8

DevSecOps: seguridad integrada en el pipeline
SAST, DAST, dependency scanning, gestión de secrets, signing de imágenes y compliance automatizado.
›
Conceptos teóricos en profundidad
  • SAST (Static Application Security Testing): Análisis del código fuente sin ejecutarlo. Detecta: SQL injection, XSS, hardcoded secrets, uso de funciones inseguras. Herramientas: Semgrep (reglas personalizables), SonarQube, Bandit (Python), Gosec (Go). Se integra como job en el pipeline, falla si hay hallazgos críticos.
  • DAST (Dynamic Application Security Testing): Ataca la app en ejecución. Detecta vulnerabilidades de runtime que SAST no ve (autenticación rota, headers faltantes). OWASP ZAP en modo CI. Se ejecuta contra el entorno de staging, no producción.
  • Dependency scanning: Las dependencias son el mayor vector de vulnerabilidad (Log4Shell, eventos NPM maliciosos). GitLab tiene dependency scanning nativo. OWASP Dependency-Check para Java. Snyk para múltiples ecosistemas. Política: bloquear si hay CVE CRITICAL en dependencias directas.
  • Gestión de secrets en CI: Nunca en variables de entorno en texto plano en el YAML. Niveles: (1) Variables del CI encriptadas, (2) Vault (HashiCorp) con AppRole auth, (3) External Secrets Operator + cloud secrets manager. Secret scanning: detect-secrets, GitLeaks para detectar secrets accidentalmente commiteados.
  • Container signing: Cosign + Sigstore. Firmar la imagen al buildear. Verificar la firma antes de deployar. Policy controller (Kyverno, OPA Gatekeeper) rechaza imágenes sin firma válida en el cluster.
  • Observabilidad en pipelines: Métricas de pipeline: duración, tasa de fallo, frecuencia. OpenTelemetry para tracing de pipelines. Alertas cuando el pipeline falla más del X% en 24h. Dashboard de salud de pipelines en Grafana.
Ejercicios prácticos
  • Integrar Semgrep en GitLab CI: crear reglas custom para detectar patrones inseguros en el código del equipo
  • Configurar GitLeaks como job de pre-pipeline: detección de secrets en el historial del repo
  • Implementar Cosign: firmar imagen en CI, verificar firma con Kyverno en k8s

Arquitectura del laboratorio local Recursos limitados
Diseñado para correr en una laptop con 8GB RAM y 4 CPU cores. Uso estimado: ~4GB RAM, ~20GB disco.
k3d
Kubernetes ligero (k3s en Docker). 1 control-plane + 2 workers. Usa ~800MB RAM. Alternativa a minikube.
GitLab CE (alternativa)
Si los recursos no alcanzan: Gitea + Forgejo como alternativa. O usar GitLab.com (free tier) con runner local.
ArgoCD
Instalado en el cluster k3d. Namespace: argocd. Acceso via port-forward o Ingress local.
Registry local
Docker Registry v2 local (registry:2). k3d configurado para trust sin TLS. Evita push a Docker Hub.
NGINX Ingress
Ingress controller en el cluster. Expone servicios en localhost via port 80/443.
GitLab Runner
Runner en Docker en el host (no en k3d). Docker-in-Docker para builds de imágenes.

Paso a paso: montar el laboratorio
  1. Instalar prerequisitos: Docker Desktop (o Docker Engine en Linux), kubectl, k3d CLI, helm, argocd CLI. En macOS: brew install k3d kubectl helm argocd
  2. Crear registry local: docker run -d --name registry -p 5000:5000 registry:2
  3. Crear cluster k3d con registry: k3d cluster create lab --servers 1 --agents 2 --registry-use k3d-registry.localhost:5000 -p "80:80@loadbalancer" -p "443:443@loadbalancer"
  4. Instalar NGINX Ingress: helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx && helm install ingress-nginx ingress-nginx/ingress-nginx -n ingress-nginx --create-namespace
  5. Instalar ArgoCD: kubectl create namespace argocd && kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
  6. Obtener password inicial de ArgoCD: argocd admin initial-password -n argocd
  7. Configurar GitLab CI runner: docker run -d --name gitlab-runner --restart always -v /var/run/docker.sock:/var/run/docker.sock gitlab/gitlab-runner:latest — luego registrar con token del proyecto
  8. Clonar proyecto ejemplo: git clone https://github.com/tu-usuario/lab-cicd-app — o crear uno nuevo: Express.js API simple con /health y /api/items endpoints
  9. Crear repos: app-repo (código + .gitlab-ci.yml) y config-repo (manifiestos k8s de la app)
  10. Crear ArgoCD Application: apuntando al config-repo, namespace default, auto-sync habilitado
  11. Hacer primer commit en app-repo: el pipeline debe ejecutarse end-to-end y el cluster quedar con la app running
  12. Verificar: curl http://localhost/health — debe devolver 200 OK con {"status":"ok"}
Escenarios prácticos del laboratorio
  1. Fallo de pipeline: introducir un test que falla → pipeline se detiene, deploy no ocurre → corregir → pipeline verde → deploy
  2. Rollback GitOps: deployar imagen rota (app que crashea) → ArgoCD detecta pods crasheando (si usas Argo Rollouts) → git revert del commit de imagen → ArgoCD sincroniza → cluster vuelve a versión anterior
  3. Cambio de configuración: cambiar una variable de entorno en el ConfigMap del config-repo → ArgoCD detecta OutOfSync → sincroniza → pods se reinician con nueva config
  4. Despliegue progresivo: instalar Argo Rollouts → cambiar Deployment a Rollout con estrategia Canary (10% → 25% → 50% → 100%) → deployar nueva versión → observar el progreso → aprobar manualmente cada fase
  5. Scan de seguridad con fallo: introducir una dependencia con CVE conocido → Trivy falla el pipeline → pipeline se detiene antes del push → corregir dependencia → pipeline verde

Kubernetes local ligero. Cluster completo en Docker. Ideal para recursos limitados. Alternativa: minikube.
ArgoCD
GitOps controller. Sincroniza el cluster con el estado en Git. UI web + CLI. App of Apps pattern.
Semgrep + Trivy
SAST de código fuente (Semgrep) y scanning de imágenes (Trivy). Ambos se integran como jobs en el pipeline.
Helm + Kustomize
Helm para templating complejo. Kustomize para overlays por entorno. ArgoCD soporta ambos nativamente.
Argo Rollouts
Despliegues Canary y Blue/Green avanzados en Kubernetes. Analysis runs para rollback automático.
Grafana + Loki
Observabilidad de pipelines y apps. Logs de jobs, métricas de deployments, alertas de fallo.
No instalar todo a la vez. El laboratorio tiene un orden: Docker → k3d → ArgoCD → Runner → primer pipeline → luego herramientas adicionales.
